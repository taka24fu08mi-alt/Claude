ひと目でわかる要約

うまくいっている点：コーディネーター（司令塔）として使えています。このセッションを「マスター」と名付け、最初に役割を与え、各作業を1つずつ確認する代わりに、複数セッションの進捗をまとめて出させました。この「ハブ＆スポーク」の習慣は、並行作業を回す土台として優秀で、会話が実装の細部に流れず、全体の把握に集中できました。

つまずいている点：Claude側の問題として、最初の進捗報告が自信過剰でした。世界標準時（UTC）の時刻を日本時間として書き、さらに、出力が途中で切れていただけなのに「デスクトップへの保存はされていない」と書きました。2点とも Claude 自身が後で訂正しましたが、事後でした。ユーザー側では、タイムゾーンや「不確かな結果の扱い方」といった常設の指示がまだ無く、Claude が日本のユーザーに合わない標準設定で動いてしまいました。

すぐできる改善：「マスターセッションの状況確認」をカスタムスキルにして、1つのコマンドでセッション一覧・日本時間への変換・「確認済み」と「未確認」の区別までやらせる。セッション開始時にフックで日本時間の現在時刻を自動で入れる。CLAUDE.md に「時刻はすべて日本時間で書く／出力が切れていたら明記する」と1行足せば、今回の2つの誤りは防げます。

大きな展開：モデルが進化すれば、マスターは報告係から「実際の指揮役」に進めます。並行して動く作業セッションに仕事を振り、定期的に進み具合を確認し、止まったセッションの仕事を振り直し、本当に判断が要る時だけユーザーに戻す、という形です。そのために、作業セッションには「自己申告の進捗」ではなく「テスト合格・コミット・出典付きのファイル更新時刻」など客観的な証拠で報告させておくと、マスターの見立てを任せて動かせるほど信頼できます。

使い方の特徴

1セッション（7メッセージ・約1時間）だけなので、全体像ではなく「スナップショット」として見てください。それでも、コードを書く道具というより、司令塔（オーケストレーション用ハブ）として Claude Code を使っていることが読み取れます。最初にこのセッションを「マスター」とし、作業全体の進捗確認を頼みました。Claude はリモートセッションを一覧し、Bash で軽く確認して答えました。ファイル編集・コミット・特定言語の作業はありません。複数の Claude セッションを中央から束ね、実装を1行ずつ指示するのではなく、プロジェクトの高さから見守るスタイルです。


指示は短く、役割中心です。細かい仕様ではなく、立場（マスターセッション）と目的（状況を報告）を渡しています。常設の指示や好みはまだ記録されておらず、タイムゾーンやセッション状態の読み方は Claude の推測任せになり、そこでつまずきが出ました。最初の報告はUTCを日本時間として表示し、切れた出力から「保存されていない」と結論づけました。Claude が自分で見つけて直しました。それに対するユーザーの反応は記録されていないため、気づいたのか、黙って受け入れたのかは不明です。


セッションの評価は「おおむね達成」。セッション検索自体は速く正確でした。このスタイルが普段の使い方なら、日本時間であること、そして途切れた・曖昧なセッション状態をどう報告してほしいかを先に伝えておくと、概要の信頼性が上がります。今は、割り込まず Claude に走らせて自己訂正させる形ですが、状況報告の不正確さが指摘されないまま通ってしまうおそれがあります。

特徴的なパターン：このセッションでは、Claude を中央の「マスター」コーディネーターとして使い、短い役割ベースの指示で各セッションの状況確認を任せ、報告の誤りも本人が直すのに任せました。

うまくいった点

2026年11月18日の1セッションに基づきます。Claude をマスターコーディネーターとして、役割設定と並行作業の状況把握に使いました。

オーケストレーション用のマスターセッション

1つのセッションを「マスター」にして、他のセッションの概要を見るために使いました。各セッションを手作業で確認する代わりに、Claude にアクティブなセッションを一覧させ、それぞれの状況を要約させています。このハブ＆スポーク型は、並行作業を管理するのに拡張しやすいやり方です。

セッションの役割を明確に与える

何かを頼む前に、まず Claude に明確な役割を与えました。セッションの目的を先に決めると、Claude は実作業者ではなく調整役として動き、会話が実装の細部にそれず、全体の見守りに集中できます。

リモートツールによる素早い状況確認

リモートのセッション一覧ツールと簡単なシェル確認を組み合わせ、数メッセージでプロジェクト全体の状況をつかみました。検索は速く、正しい情報源に当たりました。ただし細部には注意が必要です。最初の報告はUTCを日本時間として表示し、出力が切れていただけなのに保存されていないと述べました。Claude は両方を自分で訂正しました。このような状況報告では、Claude にタイムゾーンを明記させ、確認できないことは「確認できない」と言わせるのがよいでしょう。

つまずき

1セッションのみのため、つまずきは「時刻の誤表示」と「切れたデータからの断定」を含む、1回の不正確な報告に集中しています。

1. 状況報告でのタイムゾーンの思い込み

Claude はUTCの時刻を日本時間のように提示しました。訂正されるまで、進捗の概要は誤解を招く内容でした。「時刻はすべて日本時間（JST）で報告する」といった一文を CLAUDE.md に書いておけば、Claude の自己発見に頼らずに済みます。

  • マスターセッションの最初の進捗報告で、セッションの時刻がUTCなのに日本時間と書かれ、作業が起きた時間を誤って伝えていた。
  • タイムゾーンの指示が記録されておらず、Claude には出力を照合する基準がなかった。タイムラインを信頼するには、追加の訂正が必要だった。

2. 途切れたデータからの自信ありげな結論

読んでいた情報源が途中で切れていたのに、Claude は「デスクトップへの保存はされていない」と述べました。証拠が無いことを、無かった証拠として扱っています。出力が不完全な時は知らせ、断定せずに「未確認」とするよう頼むとよいでしょう。

  • 最初の報告は保存が行われていないと述べたが、元の出力が途切れていたため、主張は根拠が無かった。
  • 保存状況の主張は Claude が自分で撤回した。最初の報告を信じて動いていたら、すでに保存済みかもしれない作業をやり直したり、心配したりしたおそれがある。

3. 司令塔セッションでの、未検証の初回まとめ

マスターセッションで概要を頼んだ時、最初のまとめはすぐ返ってきたものの、正確さは部分的でした（結果は「おおむね達成」）。複数セッションの調整では、Claude に提示前の再確認をさせるか、まとめと一緒に「不確かな点」の一覧を出させるとよいでしょう。

  • マスターの役割を与えて進捗を頼んだ後、セッション一覧は速かったが、まとめには同じセッション内で直すべき誤りが2つあった。
  • 訂正への反応は記録されておらず、訂正後の状況が望むものだったかは不明。「確信度・注意点」の行を明示的に頼めば、こうした差がすぐ見えるようになる。

試すとよい機能・提案

CLAUDE.md に足す文面の提案

① 時刻とロケール

## 時刻とロケール
- ユーザーは日本在住。時刻は常に日本時間（JST, UTC+9）で表示する。元の時刻がUTCなら変換し、明記する（例：「14:30 JST（05:30 UTC）」）。

理由：分析した唯一のセッションで、最初の進捗報告がUTCを日本時間として表示し、後で自己訂正したため。CLAUDE.md の冒頭近くに追加します。

② 状況報告のルール

## 状況報告
- 他セッションの状態（保存やデスクトップへの書き込みが行われたか等）を報告する時は、まず元の出力が途切れていないか確認する。途切れていたり不完全なら「不明（出力が途切れている）」と書く。行われなかったと断定しない。

理由：出力が切れていただけなのに「デスクトップへの保存は行われていない」と報告し、不正確な状況を伝えたため。

③ マスターセッションの役割

## マスターセッションの役割
- マスターセッションを頼まれたら、claude-code-remote MCP で全セッションを一覧し、次の列の表で出す：セッション名／現在の作業／最終更新時刻（JST）／状態（完了・進行中・停止・不明）。確認できていない項目は「未確認」と書く。

理由：役割設定→全体の状況確認という流れを、決まった形式で再現でき、推測による誤りも減るため。

試したい機能

カスタムスキル

よく使う指示をマークダウンファイルに保存し、1つのコマンドで呼び出せます。「マスターになって状況を教えて」を /status にまとめれば、日本時間への変換と途切れの確認を含んだ、同じ品質の報告が毎回出ます。

mkdir -p .claude/skills/status && cat > .claude/skills/status/SKILL.md << 'EOF'
---
name: status
description: マスターセッションとして全 Claude Code セッションの進捗を報告する
---
1. mcp__claude-code-remote__list_sessions を呼ぶ。
2. 各セッションについて、名前・現在の作業・最終更新時刻（JST=UTC+9に変換して明記）・状態を示す。
3. 出力が途切れている・曖昧なら、その項目は「未確認」とする。失敗したと推測しない。
4. 最後に、ブロッカー・次のおすすめ行動・私の判断が要る事項を書く。
EOF

フック

セッション開始などのタイミングで、シェルコマンドを自動実行できます。SessionStart フックで日本時間の現在時刻を毎回渡せば、Claude は正しい基準を持ち、UTCと日本時間の取り違えが起きにくくなります。

{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "echo \"現在時刻: $(TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M JST')\"" }
        ]
      }
    ]
  }
}

ヘッドレスモード

スクリプトやcronから、対話なしで Claude を実行できます。複数セッションをよく確認するなら、マスターセッションを毎回開かずに、状況のダイジェストを自動で作れます。

claude -p "/status" --allowedTools "mcp__claude-code-remote__list_sessions,Bash" > ~/session-status-$(TZ=Asia/Tokyo date +%Y%m%d-%H%M).md

使い方のコツ

推測ではなく「確認できた事実」を求める

状況報告を頼む時は、確認したことと推測したことを分けるよう伝えます。今回の2つの誤り（時刻・保存状況）はどちらも、Claude が空白を思い込みで埋めたことが原因でした。「確認済み／推測」の区別を頼めば、不確かさがその場で見え、あとから訂正する必要がなくなります。ユーザーが要約に頼るマスターの役割では特に重要です。

コピーして使える指示文

あなたはマスターセッションです。全セッションを一覧し、進捗を表にまとめてください（時刻は日本時間）。各項目に「確認済み（出力で直接見た）」か「推測」かを付け、出力が途切れていた場合は、その旨を明記してください。

報告の前に自己チェックさせる

Claude は自分の間違いに気づけましたが、それは誤った報告を出した後でした。回答の前に時刻と完全性を確認させれば、訂正が報告より前に済みます。プロンプトに1文足すだけで、誤解を招くまとめを避けられます。

コピーして使える指示文

最終報告の前に確認してください：(1) すべての時刻が日本時間になっているか、(2) 途切れた出力に頼った結論が無いか。そのうえで報告してください。

最適化の前に、履歴をためる

今回の分析は7メッセージの1セッションだけで、複数セッションで繰り返された指示はまだありません。時刻と報告のルール（CLAUDE.md）という基本を整え、マスターセッション運用を1〜2週間続けてから見直すと、作業の分け方などのパターンがはっきりします。

コピーして使える指示文

CLAUDE.md を読み、「時刻とロケール」「状況報告」のルールに従うことを確認してから、全セッションの現在のプロジェクト状況を教えてください。

これからの可能性

AI開発支援は、単発のチャットから、並行する多数のサブセッションを動かし・監視し・点検する「司令塔エージェント」へ移りつつあります。

1. 並行する作業エージェントを指揮するマスターセッション

マスターは状況報告にとどまらず、複数のリモート Claude セッションに並行して仕事を渡し、進み具合を定期的に確認し、終わった・止まったセッションに新しい仕事を割り当てられます。プロジェクトの区切りまで、人が付きっきりでなくても進み、判断が要る時だけユーザーに戻ります。

試し方：claude-code-remote の MCP ツール（list_sessions と、送信・起動系のツール）を、マスター・作業者の役割と受け渡しルールを書いた CLAUDE.md とともに使います。各作業者には git worktree で独立したブランチを持たせます。

コピーして使える指示文

あなたはこのプロジェクトのマスターセッションです。まず list_sessions を呼び、稼働中の全セッションを表にしてください：役割・現在の作業・最終更新時刻（日本時間・明記）・直近の作業が保存/コミット済みか。次に、プロジェクトの TODO やロードマップを読み、残りの作業を並行して進められる独立したタスクに分けてください。各タスクを空いているセッションに割り当てるか、新しい作業セッションを提案し、目的・対象ファイル・「完了の定義（テスト合格を含む）」を明記してください。進捗は定期的に確認し、作業者が終えたら、完了にする前に自分で出力を検証（テスト実行・差分確認）してください。設計上の判断や、繰り返す失敗のときだけ私に知らせてください。

2. 証拠つきの、自己検証する状況報告

今回のつまずきは、確認せずに時刻や保存状況を事実として書いた報告から生じました。検証を先に行う報告の流れなら、すべての主張に出典（gitログの行・ファイルの更新時刻・ツールの出力）を付けさせ、曖昧なデータ（途切れた文章など）は推測せず「未確認」にできます。UTC/JSTの取り違えや保存状況の誤りは、ユーザーに届く前に防げます。

試し方：CLAUDE.md に「すべての主張は、元になったコマンド出力を示す」というルールを書き、報告の前に Claude に Bash（git log、ls -la、date など）で保存状況と時刻を確認させます。

コピーして使える指示文

全セッションの進捗報告を作ってください。ただし次の検証手順を厳守すること。(1) 書き始める前に `date` と `TZ=Asia/Tokyo date` を実行し、UTCとJSTの現在時刻を確定する。すべての時刻はJSTで、「JST」と明記して示す。(2) 各セッション・作業ごとに、保存/コミットの状況を実際のコマンド（git status、git log -5 --format='%h %ad %s' --date=iso、対象ファイルへの ls -la）で確認する。要約だけから状況を推測しない。(3) 元のデータが途切れている・欠けている・曖昧な場合は、その主張を「未確認」とし、何が足りないか説明する。推測しない。(4) 最後に「確信度」の節を設け、確認済みの主張と推測の主張を分けて挙げる。その後、自分の報告をもう一度読み、コマンド出力の裏付けが無い主張を直す。最終的な報告は、セッション｜役割｜最終更新（JST）｜状態｜根拠｜次の一手、の表で出す。あわせて、今後のセッションでこれらのルールを守らせるための CLAUDE.md の追記案も出してください。

3. テスト駆動で自走する作業ループ

マスターが各作業者に「調子はどう？」と聞く代わりに、作業者が自分で閉じたループを回せます。失敗するテストを書き、実装し、テストを実行し、全部通るまで繰り返す。完了した時か、N回試して詰まった時だけマスターに報告します。マスターの進捗把握は、自己申告ではなく客観的な信号（テスト合格・コミット）に基づくものになり、夜間に複数の機能を作らせることも可能です。

試し方：作業者にはヘッドレスモード（claude -p）かリモートセッションを使い、編集のたびにテストを走らせるフックを加えます。各作業者は状況を共有の JSON ファイルに書き、マスターがそれを読みます。

コピーして使える指示文

この機能を、テスト駆動のループで自走して作ってください。1) 要件を読み、それを表す失敗するテストを書き、「test: <機能名>」でコミットする。2) 通る最小限の変更を実装し、全テストを実行して、失敗を注意深く読む。3) 全テストが通るまで手順2を繰り返す（最大8回）。上限に達したら止まり、ブロッカーの要約を書く。4) 各回のあとに .claude/status.json へ1行追記する（時刻(JST)・回数・合格/不合格の数・一言メモ）。5) 全部通ったら、リンターと型チェックを実行して問題を直し、コミットし、状態「done」とコミットハッシュを最終エントリに書く（マスターが検証できるように）。
