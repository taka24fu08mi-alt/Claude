Master Session Orchestrating Parallel Worker Agents
Your master session could do more than report status. It could hand tasks to several remote Claude sessions running in parallel, check their progress on a schedule, and assign new work to sessions that finish or stall. A whole project milestone could then move forward unattended, with the master only coming back to you when a decision is needed.
Getting started: Use the claude-code-remote MCP tools (list_sessions plus any send or spawn tools) with a CLAUDE.md that defines the master's role, the worker roles, and the handoff rules. Use git worktrees so each worker has its own isolated branch.
Paste into Claude Code:
You are the MASTER session for this project. First, call list_sessions and build a table of every active session: its role, current task, last activity time (converted to JST, UTC+9, and labeled explicitly), and whether its latest work is committed or saved. Next, read the project's TODO or roadmap and split the remaining work into independent tasks that can run in parallel. Assign each task to an idle session or propose a new worker session for it, with a clear goal, the files in scope, and a definition of done that includes passing tests. Check on progress periodically. When a worker finishes, verify its output yourself (run its tests, read its diff) before marking the task complete. Escalate to me only for architectural decisions or repeated failures.
Self-Verifying Status Reports With Evidence
The friction in this session came from a report that stated things as fact (times, save status) without checking them. A verification-first reporting workflow could require every status claim to come with a source, such as a git log line, a file timestamp, or tool output. Ambiguous data, like truncated text, would be flagged as 'unverified' instead of guessed. The reports would then be trustworthy enough to act on without re-checking.
Getting started: Add a reporting rule to CLAUDE.md that every claim must cite the command output it came from. Have Claude use Bash (git log, ls -la, date) to confirm saves and timestamps before reporting.
Paste into Claude Code:
Generate a project progress report, but follow these verification rules strictly: (1) Before you write anything, run `date` and `TZ=Asia/Tokyo date` to establish the current time in both UTC and JST. Show every timestamp in JST with the label 'JST'. (2) For each session or workstream, confirm its save or commit status with real commands (git status, git log -5 --format='%h %ad %s' --date=iso, ls -la on the relevant files). Never infer status from summaries alone. (3) If any source data is truncated, missing, or ambiguous, mark that claim as UNVERIFIED and explain what is missing. Do not guess. (4) End the report with a 'Confidence' section listing which claims are verified and which are inferred. Then reread your own report once and correct any claim that is not backed by command output.
Autonomous Test-Driven Worker Loops
Instead of the master asking each worker 'how's it going?', workers could run closed loops on their own: write a failing test, implement the change, run the suite, and repeat until everything is green. A worker would report to the master only when it is done or has been blocked after N attempts. The master's progress view would then rest on objective signals (tests passing, commits made) rather than self-reported status. Multiple features could be built overnight this way.
Getting started: Use headless mode (`claude -p`) or remote sessions for the workers, plus a hook that runs tests after each edit. Have each worker write its status to a shared JSON file that the master reads.
Paste into Claude Code:
Work on this feature autonomously using a test-driven loop. 1) Read the requirements and write failing tests that capture them, then commit with the message 'test: <feature>'. 2) Implement the smallest change that could pass, run the full test suite, and read any failures carefully. 3) Repeat step 2 until all tests pass, for at most 8 iterations. If you hit that limit, stop and write a blocker summary. 4) After each iteration, append a line to .claude/status.json with the timestamp (JST), the iteration number, the pass/fail counts, and a one-line note. 5) When everything is green, run the linter and type checker, fix any issues, commit, and write a final status entry with state 'done' and the commit hash so the master session can verify it.
